# Sal POS — release candidate

Current development build: **1.0.38-rc.1**. Physical hardware acceptance, seller support details and a signing identity are still required before a customer release. See [store setup](docs/STORE-SETUP.md), [hardware support](docs/HARDWARE-SUPPORT.md), [support](docs/SUPPORT.md) and [releasing](docs/RELEASING.md).


Electron desktop register with an Express API and a local sql.js database. Version 1.0.37 repairs sale persistence, refunds, tender reporting, access control, local product storage, and backup restore.

## Development

Requires Node.js 22.14+ and npm. On Windows:

```sh
npm ci
npm run check
npm test
npm start
```

Receipts use Electron's Windows printer driver interface; the cash drawer uses the Windows spooler. The obsolete native printer package has been removed. Test your printer and drawer in Settings → Hardware before using a register.

Build an installer with `npm run dist` (unsigned pilot) or `npm run dist:release` (configured signing required). Builds exclude shop databases, sales, credentials, backups, and tests. Release artifacts belong in GitHub Releases, generated by electron-builder; pushing source alone does not distribute an application update. The update repository is `offers-png/sal-pos-`.

## First run and access

- Create an owner account on the first-run screen with a 6–12 digit PIN. New installations have no default account.
- Existing accounts remain intact. An account using the old `1234` PIN must change it at login.
- Sessions use HttpOnly, SameSite cookies and expire after 12 hours. Login and manager-PIN attempts are rate-limited.
- Cashiers can sell, view products, log drawer/ID events, and operate shifts. Product/settings changes, refunds, voids, administrative reports, user management, and backups require a manager or owner. A manager PIN can authorize an action from the register.
- The server listens only on `127.0.0.1:5000`. It is not intended for LAN or Internet hosting. Sensitive files are not served by the web server.

## Upgrading and recovery

Back up the register before installing. The database stays at Electron's user-data path, normally `%APPDATA%/sal-pos/sal-pos.db` (the actual path is logged at startup). A `.pre-<version>.db` copy is created before opening an existing database for the new schema. Existing sales, products, shifts, users, and returns are preserved.

Saves use a flushed temporary file and atomic rename. Sales, stock changes, refunds, and void stock adjustments commit together. A failed disk write rolls back the in-memory transaction too.

Restore validates database integrity, makes an emergency copy, replaces the active in-memory database, and invalidates sessions. Sign in again afterward. The JSON upload limit is 32 MB, allowing roughly 24 MB of raw database data; larger backups require an offline restore with the application closed.

## Checkout and refunds

Checkout waits for a durable save before clearing the cart or showing a receipt. It calculates known-product prices on the server and checks the submitted total against the configured tax rate and discount. Money calculations use integer cents. Cash/card purchases respect product taxable flags; EBT exemption applies only to EBT-paid eligible items. The register's tax switch remains available for intentionally exempt sales.

On connection failure, the pending request stays in browser storage. Retry checkout to recover that same transaction, including after reloading. Do not clear browser storage to retry an uncertain sale. Pending checkout is retried unchanged before a new sale. Receipts include the persisted sale ID and tender breakdown.

Returns identify original sale lines, aggregate repeated lines, enforce remaining quantity, and refund the original allocated discount and tax. Return retries reuse a persistent request ID. Refunds cannot exceed the amount paid with the selected original tender. Split-tender returns may need separate item/tender requests; a single line spanning multiple tenders is not supported by the automatic refund UI and requires manual reconciliation.

“Debit Card” and “EBT” record external-terminal payments; this app does not authorize or transfer funds. Complete payments/refunds on the external terminal as appropriate. Store Credit is a recorded tender, not a customer balance ledger.

## Reports and legacy history

New sales store exact tenders. Daily and shift reports deduct refunds and use those amounts. Expected drawer cash equals starting cash plus net cash receipts. Voiding restores stock once and is blocked for sales with returns.

Older combined payments did not store separate amounts. Reports mark them as **unallocated legacy tenders**, never both cash and EBT. An open shift containing them cannot be automatically closed; reconcile using the backup and original terminal records. Old saved daily reports remain historical snapshots. Refund allocation for legacy lines without stored totals is proportional to their original line prices.

## Local store data

Products, inventory, employees, sales, returns and store settings are stored in the local database. No Google account, credentials or spreadsheet is used. Each new installation starts with an empty catalog; add products or import your own CSV in Settings. Existing databases are preserved.

Use Settings to configure business name, phone, receipt footer and tax rate, add employees, choose a Windows printer, and manage customer-screen marketing images. Use Windows Extend mode for a second screen. USB barcode scanners should use keyboard/HID mode with an Enter suffix. Product screens provide search, stock editing, reorder thresholds and a low-stock filter; receipt history supports reprinting past sales.

Back up the database to an external drive regularly. Marketing images live separately in the user-data marketing-images folder; copy that folder too when moving computers. Separate PCs have independent databases; this is not a shared multi-register server.

The Windows installer bundles the runtime. Supported targets are Windows 10/11 x64 with compatible Windows printer drivers; obsolete Windows versions and every device model cannot be guaranteed. Electron requires [Windows 10 or newer](https://www.electronjs.org/blog/windows-7-to-8-1-deprecation-notice). Internet is only needed for optional application updates.

Automatic end-of-day printing requires the register page to remain open at 11:59 PM and an authorized session. Failed attempts can retry during that minute; Print EOD provides a manual retry afterward. Reports are saved before printing and the completion marker is set only when printing succeeds.

## Verification

`npm test` covers HTTP authorization, CSRF/Host checks, static-file isolation, sale retries, invalid amounts, refund limits, concurrent returns, split tenders, product sync preservation, rollback, restore, browser checkout failure/retry, double-click prevention, and HTML sanitization. `npm run check` parses source and inline scripts. CI runs both on Windows.

Physical printers, scanners, cash drawers, and external terminals need deployment-specific checks. The software suite does not validate those devices.
